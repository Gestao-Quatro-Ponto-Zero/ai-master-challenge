# Engineering and Product Trade-offs

## Decision Matrix

| Trade-off | Option A | Option B | Decision | Benefit | Cost | Why acceptable | Revisit condition |
|---|---|---|---|---|---|---|---|
| Completeness vs temporal integrity | Maximize row coverage | Exclude fatal chronology and disclose warnings | Quarantine fatal cases; compare MAIN and STRICT | Defensible sequence evidence | Lower behavioral coverage | Quality debt remains visible and recoverable | Upstream timestamps are corrected and revalidated |
| Rich live system vs deterministic demo | Live services and changing inputs | Fixed local snapshots | Fixed deterministic demo | Repeatable evaluation with no credentials | No live ingestion | The task evaluates governed reasoning and product clarity | Production deployment is authorized |
| Predictive score vs explainable queue | Numeric individual ranking | Versioned deterministic rules | Explainable queues | Traceable inclusion and review | No forecast precision claim | No validated predictive model exists | Prospective model validation passes governance |
| Graph sophistication vs reproducibility | Full live graph stack | Bounded local graph | Bounded promoted graph | Easy local inspection | Fewer interactive capabilities | Evidence quality matters more than infrastructure breadth | Enterprise graph operations are required |
| Neo4j runtime vs NetworkX local | Mandatory graph server | NetworkX reference plus export | NetworkX local; Neo4j optional | No external dependency | Export is not a live service | Evaluators can reproduce the graph | Managed graph deployment is approved |
| Automation vs human review | Automatic intervention | Manual investigation and disposition | Manual review required | Accountable operational boundary | More reviewer effort | Evidence is historical and treatment eligibility is unresolved | Approved playbooks, consent, and monitoring exist |
| Breadth of experiments vs statistical readiness | Mark all designs launch-ready | Classify feasibility and power | Preserve eight designs with differentiated readiness | Honest planning portfolio | Fewer immediately reviewable designs | Readiness is not effectiveness | Sample and operating constraints improve |
| English submission docs vs pt-BR interface | One language everywhere | English evaluation docs and pt-BR product | Split by audience | Clear technical review and coherent local demo | Bilingual maintenance | Each surface has a distinct audience | Evaluation language requirements change |
| Dynamic AI explanations vs fixed validated copy | Runtime generation | Deterministic evidence-based messages | Fixed copy | Reproducible and auditable statements | Less conversational flexibility | No runtime AI is needed for the demo value | Grounded generation receives separate evaluation |
| Fast localization vs controlled messages | Generic lexical replacement | Complete messages and closed enum maps | Controlled messages | Correct meaning and fallback behavior | More manual copy work | Human-readable quality is a product requirement | A governed localization system is introduced |
| Single large finalization phase vs phased finalization | One broad final commit | Documentation, tooling, and process evidence gates | Phased finalization | Smaller reviewable changes and recovery points | More commits and gates | Provenance is clearer | A future release pipeline automates equivalent controls |
| Code elegance vs evaluator execution reliability | Short shell-specific package alias | Small cross-platform Node wrapper | Wrapper with one official npm command | Reliable evaluator workflow | Additional tooling code | Actual execution outranks alias brevity | npm provides an equivalent portable primitive |

## Limitations

Trade-offs reflect the fixed repository scope and historical snapshot. Costs and benefits must be reassessed before a live deployment, customer action, predictive model, or executed experiment. The accepted option is not a universal optimum; it is the human-approved fit for the documented constraints.
